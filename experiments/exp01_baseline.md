# 实验 01：单机 vs 电脑+手机分布式推理

- 日期：2026-10-27 23:40
- 模型：Qwen2.5-1.5B-Instruct Q4_K_M（1.04 GiB，1.78B 参数）
- llama.cpp：b11429（Windows CPU 版 / Android APK 同版本）

## 硬件与网络

| 角色 | 设备 | 关键参数 |
|---|---|---|
| 主节点 | 本机 | Ryzen 9 8940HX，16核32线程，32GB DDR5-5600，无独显 |
| 从节点 | vivo X90 | 天玑 9200，12GB 内存，Mali-G715 Immortalis MC11（Vulkan，11GB 可用） |
| 网络 | WiFi `deja vu 2` | 电脑 192.168.0.199 / 手机 192.168.0.200，同网段 |

网络实测（TCP 连接往返）：
- ping 最小 6ms / 平均 34ms / 最大 55ms，抖动约 9 倍
- 首次 TCP 握手 11ms

## 结果

| 测试项 | 单机（16 线程） | 电脑 + 手机（RPC） | 变化 |
|---|---|---|---|
| 预填充 pp | 223.06 t/s | **7.89 t/s** | **−96.5%**（慢 28.2 倍） |
| 生成 tg | 24.98 t/s | **3.40 t/s** | **−86.4%**（慢 7.3 倍） |

冷启动：1.04 GiB 权重推送到手机耗时约 4–5 分钟（受 WiFi 上行带宽限制），之后走手机端缓存。

## 分析

1. **拆分在这套硬件上是严重亏损**：一个单机 25 t/s 流畅可用的模型，拆开后掉到 3.4 t/s，低于舒适对话阈值（约 8–10 t/s）。
2. **预填充衰减（−96.5%）远大于生成衰减（−86.4%）**，这指向瓶颈性质：
   - 预填充是一次性传大量激活值 → **带宽敏感**
   - 生成是每 token 多次小包往返 → **延迟敏感**
   - 两者都崩，说明链路同时缺带宽和缺低延迟
3. **瓶颈不是设备算力，是网络**。手机端给出的是 Vulkan GPU + 11GB 显存，算力规格不低；但 34ms 的平均往返延迟在串行流水线上被逐 token 累加。
4. **与外部数据交叉验证**：DistAi 项目实测「PC + 一台手机跑 7B ≈ 2 t/s」，本实验「PC + 手机跑 1.5B ≈ 3.4 t/s」，模型更小、速度略高，量级一致，互为佐证。

## 结论

> 在 30ms 级 WiFi 上，dense 模型的层拆分**只增加容量，不增加速度**，且速度损失达一个数量级。
> 这独立复现了「流水线并行串行累加」的理论判断，也说明：**想验证这条路，必须先解决延迟，再谈模型。**

## 下一步（按价值排序）

1. **USB 有线对照**（`adb forward tcp:50052 tcp:50052`）：把往返延迟从 34ms 压到 <1ms，若速度明显回升，则因果链闭合——瓶颈确认为网络而非架构。
2. **切片比例扫描**（`-ts 1,0.25` / `1,0.5` / `1,0.75`）：验证「总耗时 = 各段之和」，找最优分配点。
3. **MoE 模型对照**（Qwen3-30B-A3B）：验证稀疏激活能否抵消极延迟。

## 补充实验 A：本机回环 RPC（对照组，2026-10-27 23:45）

目的：把「网络开销」从「RPC 架构开销」里剥离出来。做法是在本机 127.0.0.1 起一个 `ggml-rpc-server.exe`，走完全相同的 RPC 代码路径，但延迟接近 0。

命令：
```
ggml-rpc-server.exe -H 127.0.0.1 -p 50053
llama-bench.exe -m <模型> --rpc 127.0.0.1:50053 -t 16 -p 64 -n 32 -r 1
```

结果：

| 层级 | 配置 | 网络往返 | pp64 | tg32 |
|---|---|---|---|---|
| L0 | 纯本地（无 RPC） | — | 223.06（注1） | **24.98** |
| L1 | 本机回环 RPC | <0.1 ms | 495.67 | **20.28** |
| L2 | PC ↔ 手机 WiFi | 34 ms | 7.89 | **3.40** |

注1：L0 的 pp 用的是 `-p 128`，批大小不同不可直接与 `-p 64` 比较；tg 不受影响，可以对比。

**三档分解（tg）：**
- L0 → L1：**−19%**，这是 RPC 协议的固定税（每 token 的序列化、跨进程同步）
- L1 → L2：**−83%**，这是网络的税
- 换算成每 token 的网络停顿：`1/3.40 − 1/20.28 = 245 ms/token`；按 34ms 平均往返折算，**每生成一个 token 约需 7 次网络往返**

**反推需要的网络质量（按每 token 7 次往返）：**

| 目标速度 | 允许每次往返延迟 | 什么链路能满足 |
|---|---|---|
| 10 t/s | ≈ 7 ms | 5GHz WiFi（同房间） |
| 15 t/s | ≈ 2.4 ms | 千兆有线 / USB 网络共享 |
| 20 t/s（架构上限） | ≈ 0 ms | 本机回环 |

## 根因：链路跑在 2.4GHz

`netsh wlan show interfaces` 实测（2026-10-27 23:46）：

| 项 | 值 | 说明 |
|---|---|---|
| 无线网卡 | MediaTek Wi-Fi 6E MT7922 | **硬件支持 5GHz/6GHz，能跑千兆级** |
| 当前 SSID | `deja vu` | 扫描周边只有这一个，且只有 2.4GHz 一个 BSSID |
| 频段 / 信道 / 协议 | **2.4 GHz / 信道 4 / 802.11n** | 150 Mbps 协商速率 |
| 信号 | 98–100% | 信号不是问题，协议和频段是 |

**一条结论链**：2.4GHz 802.11n → 34ms 往返 + 抖动 9 倍 + 实测带宽 0.6 MB/s → 同时导致（a）模型下载要几十分钟，（b）RPC 推理掉 83%，（c）首字延迟无法接受。

**换言之，之前所有的“慢”，大部分是这一个配置问题的表现，而不是方案本身的天花板。**

## 修正后的结论

> RPC 架构本身只收 19% 的税（24.98 → 20.28 t/s），在零延迟下几乎无损。
> 掉到 3.4 t/s 的 83% 损失，**全部来自 2.4GHz WiFi 的 34ms 往返与抖动**。
> 因此「拆分必然慢一个数量级」这个判断需要加限定条件：**在 2.4GHz WiFi 上成立，在低延迟链路上不成立。**
